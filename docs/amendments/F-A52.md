# F-A52

**Managed git worktrees for local ACP sessions** (2026-11-19).
`POST /v1/sessions` accepts `worktree:{branch, base?}` only on a local spawn when the connected hub advertises `acpWorktree:true` (§3.2.3, §3.8.2).
Creation accepts a non-bare main or linked checkout, including a subdirectory, but refuses submodules (§3.2.7).
By default the hub creates `<main-root>-wt/<branch-with-slashes-replaced-by-hyphens>`.
When `worktreeRoot` is set, the hub mirrors the main checkout's full path under it: for `/home/u/proj/app`, root `/srv/wt` and branch `feat/x`, the destination is `/srv/wt/home/u/proj/app/feat-x`.
The hub creates missing parent directories and leaves them in place after rollback or removal.
The configured root may be inside a checkout, but the destination must be outside the repository's common git directory, even when that directory is separate or reached through a symlink.
Setting `worktreeRoot` to `/` places the worktree directly in the main checkout at `<main-root>/<flattened-branch>`; an occupied name returns 409.
Prefer a root outside any checkout or ignored by the checkout containing it.
If git reports a separate metadata directory from a linked checkout and cannot identify the main root, the hub refuses rather than guessing a destination.
An occupied or still-registered path or a branch listed as checked out is 409; another failure of `git worktree add`, including a checkout filter failure, is `internal` (HTTP 502) with git's first error line.
The hub uses an existing local branch as is, or creates one without upstream from the resolved base commit (default: this checkout's HEAD).
Both names are checked before git runs; the client supplies no destination path.
The new root becomes the session's `cwd`, and `acp.managedWorktree:{path, branch, mainRoot}` records ownership across restart and revive, separately from the web's inferred `worktree` string.
Changing or unsetting `worktreeRoot` affects only future creations; removal still uses the recorded path and ownership marker.
Git runs outside the session actor, so other sessions on the connection and hub shutdown do not wait for it.
During unpublished creation, including rollback, every `acp.open` (even an attach without `spawn`) and every ACP action except the first `acp.kill` get 409 rather than queuing; `acp.detach` is still handled normally.
That first kill, with or without `forget`, requests cancellation and waits for cleanup: even if creation fails independently, the kill succeeds if nothing is left and returns an error if a leftover is reported.
During explicit removal, only an `acp.open` requesting a worktree, `acp.remove_worktree`, `acp.revive` and `acp.kill` (with or without `forget`) get 409 because of the removal; ordinary attach, detach, prompt, seen and other actions follow their usual rules.
If session creation is refused after checkout, the hub rolls the clean worktree back without force, leaves the branch, and reports the remaining path if removal fails.
Only an interrupted `worktree add` can trigger forced removal: before any agent runs, the hub checks that it still owns the reserved directory, unlocks the incomplete worktree and force-removes it, reporting any leftover.
If the hub stops in the middle of creation, its git process group is killed on orderly shutdown, but the checkout may be incomplete and locked with no session record.
A panic in the git creation task can also skip rollback and leave a marked worktree without a session record; use the same manual recovery below.
Inspect `git -C <main-root> worktree list --porcelain` and the checkout before recovering it by hand: if locked, run `git -C <main-root> worktree unlock -- <path>`, then `git -C <main-root> worktree remove --force -- <path>` only if its contents may be discarded.
`DELETE /v1/sessions/{sid}/worktree` requires control scope and removes only that session's recorded worktree while the agent is stopped.
The hub verifies `workbench-session` in the worktree's private git directory before removal: if the checkout is gone or its marker is missing or names another sid, it clears the record and answers 404 `not_found`, “session worktree already gone; record cleared; nothing deleted”.
This also leaves unmarked worktrees created by an older hub on disk.
An absent record also returns 404; a running agent or refusal by git's cleanliness check returns 409.
Modified files and non-ignored untracked files prevent removal; everything git ignores is deleted with the worktree, including local configuration such as `.env` and nested repositories with their unpushed commits.
If removal is killed, some tracked files may already be deleted; the record remains, and another non-forced removal can refuse until the operator inspects and restores the checkout.
Normal removal leaves the branch and clears the record on success; killing or forgetting an accepted session never removes its worktree, so forgetting leaves the checkout on disk.
The saved `cwd` is unchanged; if it no longer exists, revive refuses with 409 `not_revivable` before attempting to start the agent.
The optional `git` executable in `hub.json` enables this capability; `services.workbench.gitPackage` defaults to `pkgs.git` (§3.7.2).
`services.workbench.worktreeRoot` defaults to `null`, which omits `worktreeRoot` from `hub.json`; a configured root must be absolute and contain no component named `.`, `..` or `.git`.
Git has bounded output and per-call deadlines (120 s for `worktree add` and `worktree remove`, otherwise 30 s); the hub starts no shell and disables interactive prompts and hooks.
Git uses the repository's and user's own configuration with the hub's `HOME`, `XDG_CONFIG_HOME` and `PATH`; checkout filters must resolve on that `PATH` or name an absolute executable, and a required filter that cannot run fails the request.
This sets a working directory; it does not confine the agent to it.
There is no remote worktree creation, caller-requested force removal, fetch, branch deletion, PTY or page change.
